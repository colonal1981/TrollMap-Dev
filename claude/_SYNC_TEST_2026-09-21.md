# ANSWERED, same evening. And none of the three predictions above was right.

Ryan pressed **Sync now** and the answer is the second outcome with the duplicate half removed:
**a synced repo file reaches the project's SEARCHABLE knowledge and never appears as a project
doc.** Two collections, two different doors, and only one of them has a path you can address.

## What was measured

    project_search "greppable in 1.5 seconds ..."   -> claude/_SYNC_TEST_2026-09-21.md, full text
    project_search "SAME_PLACE_M"                   -> js/data/access-index.js, full text, and
                                                       test/the-placeholder-is-not-a-name.test.js
    project_info                                    -> 320 docs, every one a claude/*.md project
                                                       doc. ZERO repo files.
    project_read "claude/_SYNC_TEST_2026-09-21.md"  -> No doc or file at that path
    project_read "Worker/research/storage.js"       -> No doc or file at that path

`SAME_PLACE_M` is the discriminator that makes this a measurement rather than a guess: it exists
in `js/data/access-index.js`, committed at 15:54 tonight in `994973f`, and in **none** of the 321
docs. It came back with the surrounding source. `test/the-placeholder-is-not-a-name.test.js` was
created tonight and came back too. **The sync is current to the last push.**

## The four things this settles

**1. THE SYNC IS MANUAL AND THERE IS NO SETTING.** Anthropic's own Help Center page for the GitHub
integration offers exactly one control — *"You can click 'Sync now' to fetch the latest changes from
your repository"* — and advises refreshing it *"periodically … and especially before starting a new
analysis."* No interval, no toggle, no automatic mode. **And no session can trigger it:** the
`Projects` tool has `project_info`, `project_read`, `project_search`, `project_write`,
`project_delete`, `project_memory_list`, `project_memory_read`, and nothing that touches a sync
source. Ryan pressing the button is the only mechanism that exists. Ask him to press it after a
push whose content matters to the next session.

**2. A REPO FILE IS SEARCHABLE AND NOT READABLE BY PATH.** `project_search` reaches it;
`project_info` does not list it and `project_read` refuses it. So a doc that must be *read whole* —
`00_START_HERE.md`, which this project's own instructions name — has to stay a project doc. A doc
that only ever needs to be *found* can live in the repo.

**3. THE REPO HALF DOES NOT SPEND THE 2 MB DOC BUDGET.** `project_info` reports
`knowledge_size: 1,634,793` against `max_knowledge_size: 2,000,000` while **14.7 MB of tracked repo
is indexed and answering searches.** The cap is on project docs. This is the reason the migration is
worth doing at all: 2.65 MB of docs on the drive, a 2.0 MB ceiling, and a prune conversation that
has come up twice.

**4. THE COLLISION IS REAL AND HAS NOT HAPPENED YET.** `claude/` in the repo holds this one file;
all 320 names in `project_info` are project docs. Nothing is in both places. **Keep it that way** —
a doc in both halves returns twice from `project_search` under the same `name` with different
`doc_uuid`s, and a stale repo copy reads exactly like the live one. There is no field in a search
hit that says which half it came from.

> **ONE DOC, ONE HOME. A search hit does not say which collection it came from, so two copies of
> one name is a stale answer wearing a current one's clothes — the failure this whole project keeps
> re-finding.**

## What this makes possible, and the one thing it does not fix

A new doc written to `TrollMap-Dev/claude/` is on the drive the instant it is written, in git with
history, `grep -rl`-able in about a second and a half, and in the project's knowledge on the next
Sync now. That is the whole reason this file exists: on 2026-09-21 a session reversed the landing
rule Ryan had settled the day before, because the rule lived only in a project doc nothing on the
drive could grep. See `THE_LANDING_RULE_IS_ANNOTATE_NEVER_FILTER_2026-09-21.md`.

It does **not** fix the freshness gap. A doc pushed and not synced is invisible to the project's
search even though it is on the drive — which is the better half of the two failure modes, because
the drive copy is greppable with no sync at all.
